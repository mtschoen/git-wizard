## Discovery and cache integration

The default CLI report prints human-readable attention details and run diagnostics; only `--json` reserves stdout for strict JSON. Progress and verbose debug diagnostics use stderr during report execution; the desktop view model owns the remaining command queue.

- **MFTLib** - Windows MFT discovery uses `MFTLib.Index.FileIndex`. `MftIndexSession` owns the index and its broker session, disposing the index before the session. It assigns `MftIndexCachePolicy.DirectoryScanFileNames` to `FileIndexOptions.RetainedFileNames` and obtains a lazy source via `BrokerSession.CreateIndexSource()`, so blocks retain directories plus `.git` and bare-repository `HEAD` markers. Null retention selects a full scan, an empty list retains directories only, and names add case-insensitive file retention. Discovery queries `FileIndex.Search` with `NameMatchMode.Exact` for ".git" and "HEAD", plus `FileEntry.Parent`, applies consumer scope/ignore policy to entry paths translated onto each drive's real indexed root (`TranslateToRealRoot`), then validates candidates through the Windows filesystem boundary. Linux and `--no-mft` retain recursive discovery. `TryDiscoverRepositoriesUsingMftAsync` returns a result that owns the session; the UI report can transfer a prepared owner for Live to adopt without another cold scan or UAC prompt.

- **Discovery scope and persistent cache policy** - Windows discovery uses GitWizard-owned persistent index blocks in one directory, `GetLocalFilesPath()/mft-index/blocks` (normally `~/.GitWizard/mft-index/blocks`). `MftIndexCachePolicy` (static) is the single source of `DirectoryScanFileNames = [".git", "HEAD"]`, the MFTLib `CacheTag` (`GWMI`, version 2) and the directory; every open and inspection caller resolves the directory through it. The `GWMI` version-2 tag identifies GitWizard's application cache semantics. MFTLib independently stamps and compares the row-shaping options, including retained file names, MFT freed-record inclusion, and enumeration walk rules. A tag or shape mismatch is reported as `CacheIdentityMismatch` for a cache-only open; the discovery coordinator rescans it when its discovery purpose requires current inventory. Blocks are never migrated. The stored metadata covers directories and retained marker names across each selected volume, potentially including other users' directory names. Search, ignore, hidden-directory and temporary-directory settings filter repository candidates after collection; they do not restrict the metadata written to the index. Live hydration can add metadata for observed ordinary files. A process running as the user can read these mapped or backing blocks. Library cache validation/locking and tag mismatch behavior follow the linked MFTLib contracts.

  - **Cache modes.** Session and discovery opens take `CacheMode`, accepting `Persistent` or `ExistingOnly` and refusing `Disabled`. Ordinary discovery and watch preparation both open cache-only with `ExistingOnly` first, then rescan only the drives their purpose requires. `MftIndexSession.CaptureDriveStatuses()` retains per-drive failures; `MftDiscoveryResult.DriveStatuses` freezes them even on unsuccessful discovery. They are not evidence of an empty repository inventory. For library cache-mode, snapshot-age and housekeeping semantics, use MFTLib's linked architecture and block-ownership docs.

  - **Ownership.** `MftIndexSession.IsFaulted` reads `BrokerSession.Ended.IsCompleted`. Disposal stops and disposes the index before disposing the session, then the `MftIndexDiagnostics` relay drains. The relay feeds `FileIndexOptions.Diagnostics` into `GitWizardLog` at Info level from a worker; the library callback only enqueues (256 records, oldest dropped, drop count logged on drain). Broker process/channel lifetime is MFTLib's contract, linked above.

  - **Local-file commands.** `ClearCache` and `--clear-cache` delete only `repositories.txt` and `report.json`; configuration and index blocks remain. `MftIndexCacheMaintenance.Clear(GetLocalFilesPath())` backs CLI `--clear-index-cache` and the sidebar Clear Index Cache action. It calls `CacheDirectory.DeleteCached` for the `blocks` directory and any leftover `v1-<64 hex>` directory from earlier releases (the only recognition of that name left, kept so Clear reclaims their disk space), then `InspectCached` for a fresh inventory. It never deletes files itself, releases an active owner, or opens a broker. Per-block failures continue; directory/inspection errors are reported. Busy drives remain while unlocked drives clear. The CLI exits 0 on success, 1 on incomplete maintenance, and does not proceed into discovery/report generation. `IndexCacheViewModel` owns Refresh (inspect, rendered by `MftIndexCacheStatusFormatter`, the same text as `--index-cache-status`) and Clear behind one busy guard for both the sidebar and the status window; its work runs off-thread and posts result/busy properties through IUiDispatcher. Inspection is point-in-time, not a permission to delete. Locks and directories remain, so Delete All Local Files continues to refuse while mft-index exists. `TryDeleteAllLocalFiles` (CLI `--delete-all-local-files`, UI Delete All Local Files) refuses while the `mft-index` subtree exists, including an empty subtree, before deleting anything; the CLI exits 1 with the reason on stderr and the UI shows "Files Not Deleted". Do not manually remove lock files while indexes are in use.

  - **Index cache status and inventory.** `MftIndexCacheInspection` inspects the cache directory (`MftIndexCachePolicy.GetCacheDirectory(localFilesPath)`). Non-Windows platforms report that MFT index cache is not applicable and bypass inspection calls without cache initialization. On Windows, an explicit directory preflight (`File.GetAttributes`) verifies the directory exists and is a directory (throwing an error for non-directories and returning empty inventory for missing paths) before calling `CacheDirectory.InspectCached`. The snapshot carries the requested `MftIndexCachePolicy.CacheTag` (`RequestedCacheTag`) and each inventory row prints the block's stored `CachedBlockStatus.CacheTag` beside it (`unavailable` when the block could not be inspected). Active session backing is captured via `MftIndexSession.CaptureCacheStatus()` and `IndexVolumeChangeSource.CaptureCacheStatus()`, returning immutable `MftActiveCacheSession` snapshots carrying volume identities and `DriveStatus` under existing disposal gates without transferring ownership. Refresh rereads in-memory statuses, including after `RescanAsync`. Status observations are point-in-time, holder identity is unavailable for held slots, and directory-entry last-write time is labeled as such rather than as scan or catch-up time. Report schema remains 2.1. Backing labels follow MFTLib's block-ownership contract.

- **Marker matching** - `GitWizardApi.SelectGitEntries` deliberately adopts the case-insensitive matching of `FileIndex.Search(new SearchQuery(GitEntryName, NameMatchMode.Exact))`. A directory named `.GIT` is therefore discovered as a repository marker, subject to the same scope and filesystem validation as `.git`. This matches NTFS's default case-insensitive behavior; do not add an ordinal post-filter. Scopes are translated onto the drive's real indexed root before comparison; for enumeration indexes over a temporary tree the root is that tree, not a synthetic drive letter. Keep filesystem validation at the Windows boundary; tests inspect entry structure rather than opening index paths.

- **Discovery ownership** - Exactly one consumer owns the transferable `MftIndexSession` at a time: discovery result -> report -> view model -> `IndexVolumeChangeSource` -> disposal. `FileIndex` is borrowed query access, not a second resource owner. Detach/take operations clear the previous holder; replacing an owner disposes the previous one. Untransferred discovery results and reports dispose their retained owner. `DiscoveryIndex` and its owner are never serialized; report schema remains **2.1** and Git metadata remains owned and reported by the existing Git repository layer. This port changes repository discovery, not Git reporting. Stopping Live detaches handlers and stops the pump before disposing the session, which disposes the index before its broker connection. Restart creates a new source and follows the same single-owner rule; a disposed, faulted, or drive-mismatched prepared owner is disposed and replaced, never reused.
- **Drive selection** - Windows drive specs are parsed by `DriveKey.TryParse` and compared as `DriveKey` values. Discovery obtains a path's volume through `WatchPath` before parsing; session and watch open inputs are drive specs. Canonical letter strings remain the reporting and platform-neutral watch interface. Discovery may reuse a prepared superset; watch arming requires the exact requested drive set.

- **Elevation integration** - WindowsDefender calls `ElevationUtilities.TryAddDefenderProcessExclusions`; tests supply a fake `IElevationProvider`. MFT discovery uses the journal broker, including when the caller is already elevated. The elevation API contract is in MFTLib's [elevation documentation](../external/MFTLib/docs/elevation.md).

- **Windows Defender setup:** On Windows, Configure Windows Defender adds process-name exclusions for `dotnet.exe`, `git.exe`, `git-lfs.exe`, `git-wizard.exe`, and `GitWizardUI.exe`. The desktop executable also hosts its elevated MFT broker. The result and process list appear in the setup alert and the in-memory Errors window; this window includes successful Defender setup diagnostics as well as errors. These exclusions reduce protection for files opened by any executable with a matching name, regardless of location; they do not exclude the executable file itself or guarantee that every Defender capability is bypassed. No MFT cache-path, temporary-directory, or volume exclusion is added.

- **Self-elevation** - Both CLI and GitWizardUI dispatch MFTLib's elevated `--broker` child mode via `ElevatedEntryPoint.RunBrokerIfRequested` (for broker-backed MFT discovery, `--watch`, and the UI's Live mode), plus the `--elevated-defender` hidden arg for Defender exclusions, before any normal/Avalonia startup.

## Desktop

`DuplicateNames` and `Largest` are inapplicable to repository discovery: discovery
does not group arbitrary duplicate names or rank file sizes. `HEAD` markers supply
bare-repository candidates through `SelectBareCandidates`; ordinary and gitfile
repositories are selected from `.git` markers. Recursive roots (Linux, confirmed
non-NTFS roots and `--no-mft`) use the enumeration producer, which applies the same
`RetainedFileNames`.

- **Desktop single instance:** `GitWizardUI.Program.Run` dispatches the MFTLib
  broker and Defender child modes before evaluating the mutex name or touching
  Avalonia. `DesktopInstance` uses a stable named mutex scoped to the current OS
  user across sessions; Windows names include the user's SID. Ownership is taken
  with `WaitOne(0)` and held synchronously through the desktop lifetime, released
  in `finally` on the same thread. Abandonment transfers admission ownership.
  A duplicate reports `git-wizard is already running`, shows a native Windows
  notice where applicable, and returns 1 without starting the application.
  Do not move this rule into MFTLib, the CLI, App initialization, or the screenshot
  executable. It does not describe canonical-versus-private MFT backing and must
  not change the library's private fallback. Startup tests use unique mutex names
  and distinct threads because same-thread mutex waits are recursive.

- **IUpdateHandler** - Interface for progress reporting, used by both CLI (UpdateHandler) and GitWizardUI (MainViewModel).
- **Repository projection and rows** - `MainViewModel.RepositoryList` owns repository node collections, row materialization and replacement, cached-report pre-population, UI path pruning, visible rows, selection, filter/group/sort modes and search debounce. Row addition, batch addition and completion updates take an explicit `streaming` argument from their refresh or Live caller. `MainViewModel` owns refresh state and clears `IsScanning` when its UI command drain applies repository arrivals. `RepositoryListViewModel.ApplyFilterAndGrouping()` builds a new `ObservableCollection` off-screen and swaps it on the UI dispatcher with the view's scroll/selection hooks. `StatusHeaderViewModel` receives the visible-row counts after the swap.
- **UI command queue** - Background refresh threads enqueue `RepositoryUICommand` structs; the first enqueue of a burst starts one 250 ms batching window on the injected `TimeProvider`, and its expiry posts one drain to the UI dispatcher that applies the whole batch and the latest progress; `DisposeAsync` stops the window.
- **RefreshStatus enum** - Per-repo status (Refreshing/Success/Timeout/Error) drives the status icon in column 0. `MarkRefreshFailed()` on `GitWizardRepository` handles timeout/error paths.
- **Header and prepared-session composition** - `MainViewModel` exposes `StatusHeader` (`StatusHeaderViewModel`, which owns `HeaderText`, the refresh-summary baseline, and filter/group suffix recomposition) and `PreparedDiscoveryIndex` (`PreparedDiscoveryIndexStore`, which owns the single prepared `MftIndexSession` between discovery and Live watch startup, disposing any prior owner on replacement).

## Discovery coordinator

- **Discovery coordinator** - `GitWizard/Discovery/RepositoryDiscoveryCoordinator*.cs` backs every entry point (CLI report/scan/tags/branches, `--watch`, desktop refresh, desktop Live). `DiscoveryScope.Create` classifies each expanded search root and retained root by filesystem through the injectable `ClassifyRoot` boundary: NTFS roots drive index discovery, confirmed non-NTFS/network roots and explicit `--no-mft` use enumeration-backed discovery scoped to those roots (`EnumerationDiscovery`: one uncached `ProducerKind.Enumeration` `FileIndex` per root, opened without a broker on any OS, rescanned on every ordinary run, with `RetainedFileNames = [".git", "HEAD"]` and a `DirectoryWalkOptions` that prunes `.git`, the dot and Hidden-attribute directories when hidden directories are skipped, the expanded ignore list and the concrete temp directories from `TempDirectories.ExpandConcretePaths`; the same `SelectRepositoryCandidates` query then runs over it; an exhausted block or `AccessDeniedSubtreeCount > 0` marks the root incomplete; symlinked directories and repositories nested in bare repositories are the accepted differences from the old walk), and an unknown filesystem is a visible error, never permission to crawl. `CandidateAdmissionPolicy` (`GitWizard/Discovery/`) owns candidate admission for the indexed filter, watch replay and Linux retained roots: an ignored root rejects itself and every descendant, `skipHiddenDirectories` rejects a dot-prefixed or Hidden-attribute directory between the search root and the candidate, and temporary directories are rejected unless opted in or the search root is itself temporary. It takes plain paths and flags, shared by every route. The selected NTFS drive set is computed once from configured scope plus the request's retained exact roots and passed through discovery, prepared owner, and watch arming.

  - **Outcomes and publication.** Every discovery reports `CompleteEmpty`, `CompleteNonempty`, `Partial`, or `Unusable` (`DiscoveryInventory`, with per-root `RootObservation`s, per-drive errors, and drive statuses). Only complete outcomes publish a full inventory (`CanPublishFullInventory`): complete-empty clears `repositories.txt` and publishes an empty report; unusable preserves the previous list and published report with no automatic crawl or second elevation attempt; partial reconciles the successfully observed scope and retains failed or unobserved scope, and a partial zero-result is never globally empty. A report-producing CLI run whose discovery cannot publish exits **3** (`GetDiscoveryExitCode`); explicit `--paths` runs are unaffected. Report schema stays **2.1**.

  - **Source selection.** Ordinary non-watch discovery uses `repositories.txt` when allowed (`AllowRepositoryList`, purpose `Ordinary`). On a list miss, Windows tries a cache-only `ExistingOnly` open without UAC and labels its scan age; cache misses requiring discovery use a broker-backed scan. Purpose `Rebuild` (CLI `--rebuild-repo-list`, `--sweep` without `--paths`, desktop Shift+Refresh) always requires a current scan, never a warm snapshot. Sweeps bypass the cached repository list and replace it on complete discovery; explicit `--paths` sweeps inspect only those paths. Ordinary report output retains its cache behavior. Bare repositories are found through retained `HEAD` markers and validated by `objects` + `refs` layout; internal `.git` directories and unrelated `HEAD` files are excluded. Replay candidates (journal changes reconciled during watch startup) get the same ignored/hidden/temp policy as indexed candidate selection.

  - **Watch startup.** `PrepareWatchAsync` (CLI `--watch` and desktop Live start/respawn) arms the platform source first, reconciles membership against the exact watched session (including retained roots outside the search roots' drives), buffers journal changes during arming, and returns a `WatchStartupResult`: inventory, arm result, source, watch volumes, and the buffered batches. `RepositoryWatchService` delivers the buffered batches through its normal ordered event path once filters are built, so changes made during catch-up are not dropped. A null source means nothing to watch: complete-empty (report and stop) or unusable (surface errors, no respawn). Linux arms fanotify marks over search plus retained roots before one recursive discovery pass per start, then consumes queued events; no MFT cache on Linux.

## Local files

GitWizard stores config and cache in `~/.GitWizard/` (overridable by `GITWIZARD_HOME`):
- `config.json` - Search paths, ignored paths, `includeTempDirectories` (temp directories -
  every profile's `AppData\Local\Temp` on Windows, the process's %TEMP%/%TMP%, and `/tmp` plus
  `$TMPDIR` on Linux - are excluded from discovery and Live by default; set true to include
  them), `skipHiddenDirectories` (directories whose name starts with `.`, or on Windows carries the Hidden attribute, are
  included in discovery and Live by default; set true to skip them)
- `repositories.txt` - Cached repo list
- `report.json` - Cached report
- `mft-index/blocks` - Persistent filtered MFT index metadata (Windows), versioned by the
  `GWMI` cache tag; not a repository list. Cleared explicitly via `--clear-index-cache`
  or sidebar Clear Index Cache (locks and directories remain). Delete All Local Files refuses while
  it exists, and Clear Cache leaves it alone

## Tips

- `deepRefresh` parameter skips expensive `git update-index --refresh` during auto-refresh; per-repo refresh button triggers it on demand.
- **Avalonia buttons call view model methods from code-behind:** the view models expose plain methods (async where needed) plus `bool` busy properties (`CanToggleLive`, `IndexCache.IsIdle`), not `ICommand` objects, so Avalonia buttons wire `Click=` handlers that call the method. Async calls go fire-and-forget through `GitWizardUI.Services.TaskFaultLogging.RunAndLogFaults` (`_ = vm.FooAsync().RunAndLogFaults("...")`), which logs any fault to `GitWizardLog` instead of leaving it unobserved. Filter/Group/Sort sidebar buttons carry their enum value in `Tag` (set via `{x:Static}` in MainWindow.axaml) and share one Click handler per row that routes it to `ToggleFilter`/`ToggleGroupMode`/`SetSortMode`.
- **Avalonia bindings don't apply the target property's `TypeConverter`** - binding a *string* to a `Thickness` property - e.g. `RepositoryNodeViewModel.ItemPaddingString` -> `Padding` - throws `InvalidCastException` on every realized row during scroll. Avalonia's default converter *does* handle string->primitive, string->enum (`FontWeight`), and string->`IBrush` (`StatusColorHex`->`Foreground`), but NOT `Thickness`. Use an explicit `IValueConverter` (`StringToThicknessConverter`) and keep the VM framework-agnostic (string in, convert in the view).
- **`LibGit2Sharp.Repository.IsValid(path)` is not fully non-throwing:** it returns `false` for a plain non-repo directory, but *throws* `LibGit2SharpException` for other conditions - notably git's "repository path ... is not owned by current user" ownership protection. `GitWizardRepository.Refresh` guards `new Repository(...)` with `IsValid` to skip stale/non-repo cache entries without spamming first-chance `RepositoryNotFoundException`, but that check lives **inside** the existing try so ownership/other errors still fall through to the catch as a normal refresh error. Don't hoist the `IsValid` call outside the try.
- **Refresh vs discovery/UAC:** ordinary GUI Refresh re-checks cached repository paths (`~/.GitWizard/repositories.txt`) without MFT discovery or UAC. A missing cache triggers discovery. Shift+click Refresh forces a fresh scan (discovery purpose `Rebuild`) without clearing the caches first; an unusable or partial outcome preserves the previous list, published report, and displayed rows instead of clearing them up front. Replacing the prepared discovery owner disposes the previous one. Starting Live transfers that owner to the coordinator's watch preparation; a disposed, faulted, or mismatched owner is replaced.
- **Temp directories are excluded by default:** discovery and Live ignore every profile's
  `AppData\Local\Temp` (any drive/profile), the process's %TEMP%/%TMP%, and `/tmp`/`$TMPDIR`,
  via the shared `TempDirectories.IsTempPath` check. A search root configured inside a temp
  directory opts that subtree back in; `includeTempDirectories: true` disables the exclusion
  globally. Test fixtures live under temp, so fixture-based discovery tests pass
  `includeTempDirectories: true` explicitly.
- **Avalonia UI updates:** `MainViewModel.SendUpdateMessage` coalesces status posts (at most one UI update in flight) so a large/recursive scan can't flood the dispatcher and wedge the window ("Not Responding"). Don't revert it to `_ui.Post` per message.
- **Refresh runs `RepositoryListViewModel.ApplyFilterAndGrouping` off the UI thread:** `RefreshAsync` awaits with `ConfigureAwait(false)`, so its tail (incl. `RepositoryListViewModel.ApplyFilterAndGrouping` and the `Repositories` swap) runs on a thread-pool thread. Avalonia *tolerates* the off-thread collection-property swap, but visual-tree access (e.g. `ScrollViewer.Offset`) calls `VerifyAccess()` and throws `Call from invalid thread`. The swap + its `AfterRepositoriesSwap` hook are therefore marshaled to the UI thread via `_ui.Post` when `!_ui.IsOnUiThread` (the off-screen build stays off-thread for the 700-repo perf win). Keep any UI-touching swap work inside that marshaled block.
- **Scroll preservation on refresh (`MainWindow.RestoreScrollAnchor`):** the `Repositories` swap resets the `ListBox` to the top. Restoring is NOT a one-shot `ScrollViewer.Offset` set - under `VirtualizingStackPanel` the scrollable extent is an *estimate* that's wrong until layout settles (AvaloniaUI/Avalonia#17460/#17848), so a single offset set lands against a stale extent and is silently clamped (the old symptom: "scroll did nothing"). The working recipe is a **closed loop**: `ScrollIntoView(anchor)` *once* to materialize it, then a bounded `DispatcherTimer` measures the anchor row's actual Y each layout pass and corrects `offset += containerY + above` until it reaches the top (converges in 1-2 passes). Don't re-call `ScrollIntoView` each pass (it re-aligns a partly-off-top row and fights the nudge -> oscillation). `ScrollIntoView` alone does NOT top-align, and a two-step ScrollIntoView trick is unreliable with variable row heights. **Headless does NOT reproduce the bug** (a single offset set sticks when layout is pumped synchronously) - validate scroll/extent timing in a real `--headed` window.
- The during-refresh jump-to-top (list empties + streams back from row 0) is a *separate, accepted* behavior, not the swap reset: `RefreshAsync` `Repositories.Clear()`s at the start and `AddRepository` streams rows back via `Repositories.Add`. Keeping scroll through the whole scan would mean not mutating the visible list during refresh (losing live per-row feedback) or an in-place diff (fights the sort/group atomic-swap perf path). Deliberately left as snap-back-after-refresh.
- **URL-valued or stale `branch.<name>.remote`, including through a conditional include:** git permits a branch's remote to be a URL ("fetch from this URL") or a remote that is no longer configured, and either can be true only via a `gitdir:` conditional include that a standalone, repository-less config read never evaluates. `GitWizardRepository.ResolveTrackedBranch` (`GitWizardRepository.UpstreamDiagnostics.cs`) is the single decision point `CollectBranches` and `RefreshRemoteDivergence` both call: it resolves the upstream through native `Branch.TrackedBranch` (which reads the repository's own config and therefore does evaluate `includeIf`), catches only `InvalidSpecificationException`, and otherwise treats a `null` result as untracked. A `Configuration.BuildFrom` read of the common repository's `config` file (never `Branch.RemoteName` or `Repository.Config`, which would drop a linked worktree's shared config - see the file header) supplies the value named in the diagnostic when `TrackedBranch` merely returns `null`; only when it throws `InvalidSpecificationException` instead - typically because a conditional include overrides an otherwise-valid base value to a URL, which that repository-less read never evaluates - does `GetEffectiveUpstreamRemoteViaGit` run `git config --null --get branch.<name>.remote` in the repository's own working directory instead, since only that (or native resolution) evaluates `includeIf`; neither read decides anything, each only names the value the diagnostic reports. The branch reports as untracked (`HasUpstream = false`, remote divergence 0/0) with one Warning per (common repository, branch, value) for the lifetime of one refresh (`UnresolvedUpstreamDiagnosticScope`, opened once per outermost `Refresh`/`GitWizardReport.Refresh` call and flowing into parallel worker branches via `AsyncLocal`), deduped across worktree paths via the common repository directory read from the gitdir's `commondir` file (falling back to the gitdir itself when no `commondir` file exists), not a path-suffix heuristic. The same unguarded `TrackedBranch` call remains in `BranchInventoryReport.CreateBranchInfo`; tracked as a follow-up issue.
