# Watch and recovery

The pipeline lives in `GitWizard/Watch/` behind `IVolumeChangeSource`. Library
behavior belongs to MFTLib's [watch lifetime](../external/MFTLib/docs/watch-lifetime.md),
[checkpoint loss](../external/MFTLib/docs/checkpoint-loss.md),
[broker lifetime](../external/MFTLib/docs/broker-lifetime.md) and
[block ownership](../external/MFTLib/docs/block-ownership.md) contracts. This page
describes git-wizard's adapters and consumers, not a second library specification.

## Windows adapter

`IndexVolumeChangeSource` owns a `MftIndexSession`, adopting a prepared owner only when it is usable and its parsed root-key set exactly matches. Otherwise it disposes that owner and opens a replacement. Fresh opens forward throttled scan progress; adopted owners do not reopen. Directory roots keep their configured identity, while watch/checkpoint observations identify their volumes. See [directory-root integration](directory-root-integration.md) for alias policy, sibling readiness and overlapping-view routing.

The adapter maps `Changed` into volume batches and consumes `WatchFaulted`. It
uses `WatchFault.IsRecovering` for recoverability, subscribes to per-drive
`WatchStateChanged`, reads `WatchStateChange.Watch.State` / `Watch.StateVersion`
and seeds from `RootStatus.Watch`. The event and recovery classification
contracts are defined in the linked MFTLib documentation.

Equal and older versions are ignored. Recovery reconciliation runs off the library callback thread and publishes CaughtUp only if its version is still current. WatchFaulted remains the source of fault diagnostics and terminal-drive policy; recoverable Faulted then Recovering transitions do not exclude the drive. No recovery timer or status polling is used.

The source records the drive's `.git` marker paths when recovery starts and, once
the recovered watch has caught up and before it publishes `CaughtUp`, delivers
the difference as ordinary change entries
(`IndexVolumeChangeSource.RecoveryReconciliation.cs`): a vanished marker as
`Deleted`, a new one as `Created`, and a surviving one as `Modified` so its
repository is refreshed. `RepositoryWatchService` applies its usual membership,
scope and refresh rules to them.

Otherwise the observation stays pending: a recoverable fault is followed, and a terminal one is excluded by its own notification. A fault that lands just after the publication is published by its handler over it. `OnWatchFaulted` excludes a nonrecovering drive and raises optional `IVolumeChangeDiagnostics.DriveFailed` while healthy drives continue. The adapter reads `RootWatchStatus.IsRecoveryStopped` for journal-warning refreshes; consumers do not infer exhaustion from failure text or a retry count. A drive that reads `Recovering` when its startup catch-up wait faults is followed the same way instead of being excluded. MFTLib's linked watch/checkpoint contracts define fault classification.

When the faulted drive reports a `JournalCheckpointLossDetection.LiveWatch` or `ScanCatchUp` loss the source first raises `IVolumeChangeDiagnostics.JournalWarningDetected` with the drive's refreshed hint; an unrelated fault raises no warning and leaves the open's standing report untouched. Arm-time `JournalCheckpointLossDetection.RootOpening` losses, including a cache-declined drive's discarded checkpoint, reach the arm result as `JournalWarning`s. The rescan that replaces a cache-only adoption clears MFTLib's `RootOpening` report, so `MftIndexSession` retains each rescanned drive's opening loss beforehand and the warning keeps its needed size; a newer library report takes precedence.

A `WatchFaultKind.CapacityExhausted` fault means the drive's block could not store at least one journal change even after growing (`RootBlockStatus.IsCapacityExhausted` reads true). It is not a watch failure: the source logs a warning that names the drive and says a rescan restores a complete index, keeps the drive usable and keeps delivering later changes, and neither excludes the drive nor raises `DriveFailed`. The source also publishes a `CapacityWarning` for the drive (its letter, the fault's message as `Detail`, and `RescanEffect`, what a rescan does) through `IVolumeChangeDiagnostics.CapacityWarningsChanged` and `CurrentCapacityWarnings`: once per drive, from the fault, and after each arm's catch-up for every watched drive whose block already reads `IsCapacityExhausted` (`Detail` is `CapacityWarning.FlaggedBeforeWatchDetail` unless the catch-up's own fault raised it). A drive's warning clears at the first watch-state change the source accepts after its published block reads `IsCapacityExhausted` false, which is when a rescan of that drive (MFTLib's recovery, for one) has published a replacement; a new arm rebuilds the set from the blocks. A capacity warning is not a `JournalWarning` and the journal warnings' ignore setting does not cover it. Discovery reports such a root as failed with the message that its index block could not store a journal change and needs a rescan, and a watch preparation rescans it (`RepositoryDiscoveryCoordinator.NeedsScan` is true for `DiscoveryPurpose.Watch`). That preparation rescan is the remedy both consumers offer: restarting Live or `--watch` rescans every flagged drive before the watch arms.

When the last usable drive is excluded the source raises `SourceDied` once and closes the output channel; a recovering drive keeps the source alive. Subscriber faults reach the reader as errors. Shutdown detaches index handlers and stops the pump before disposing its owner.

## Linux adapter

`FanotifyInterop` is the P/Invoke layer plus capability probe for the `fanotify` counterpart (`Available` / `RequiresElevation` / `UnsupportedKernel` / `UnsupportedFileSystem`, kernel floor 5.9). Probed by `LiveWatchViewModel` to enable Live mode on supported kernels and filesystems while gracefully disabling it with user-facing reasons on older kernels or unsupported filesystems.

`FanotifyVolumeChangeSource` is the `IVolumeChangeSource` backend for whole-filesystem change detection via fanotify. It emits every batch under the single routing volume `/` (`LinuxWatchRouting.Volume`, also the only startup watch volume), using marked roots only for native arming, readiness and error attribution. A directory arriving through `FAN_MOVED_TO` is emitted as `MovedIn`; file creation and file moves stay `Created`. Each decoded handle carries the event's filesystem identifier (`FileHandleKey` includes it), and `MountRootTable` remembers the marked root paths grouped by filesystem. Each decoded batch opens a short-lived descriptor on the first registered root that currently reaches the event's filesystem (a root that was renamed, removed, overmounted or unmounted is skipped because its path no longer reaches the filesystem), resolves that batch's handles through it for `open_by_handle_at`, and closes it, so no descriptor is held between batches and a plain `umount` of a watched filesystem is never blocked. Resolved paths carry the prefix of the mount that produced them: when a batch reaches a filesystem through a different root than the previous batch, or no root reaches it, that filesystem's cached handles are discarded before the cache is consulted, so a detached mount's prefix is never emitted. An event whose filesystem has no reachable root is dropped, and an event from an unmarked filesystem is skipped. Every re-arm, including empty and initialization-failed attempts, forgets the registered roots and cached handles; disposal does the same.

The library defaults stay in-process: `VolumeChangeSourceFactory.Create` and `RepositoryDiscoveryDependencies.CreateDefault` return `FanotifyVolumeChangeSource` on Linux, because only GitWizardUI dispatches the helper flag and a pkexec start of any other host would run the wrong program as root. GitWizardUI composes the helper itself: `DesktopLinuxWatchSource` (`GitWizardUI/Services`) builds the desktop's coordinator so its Linux source is `FanotifyVolumeChangeSource` when root and otherwise `ElevatedHelperVolumeChangeSource.CreatePkexec` with the desktop's own executable path passed explicitly; creating either starts nothing. The CLI never uses the helper, because `--watch` relaunches itself through sudo first. `ElevatedHelperVolumeChangeSource` is armed once: relative roots and roots this unprivileged process can prove missing (not found, or not a directory) are excluded locally, no remaining root means no launch, and otherwise it raises `IElevationConnection.Connecting`, starts `pkexec --disable-internal-agent <the executable path the desktop supplied, its own Environment.ProcessPath> --linux-watch-helper` with all three streams redirected through an injectable `LinuxWatchHelperLauncher`, and sends the arm request. `LinuxWatchHelperHost` (dispatched by `GitWizardUI.Program.Run` before the single-instance mutex and Avalonia) refuses unless the effective user id is 0, then runs `FanotifyVolumeChangeSource` and speaks `LinuxWatchHelperProtocol`, one JSON object per line with a `type` member. Requests: `arm` (`roots`, absolute paths) and `watch`. Helper frames: `hello` (`protocol`), `armResult` (`errors`, root to message), `readiness` (`volumes`: `volume`, `state`, `origin`, optional `exclusionReason` and `watchStateVersion`), `pumpStarted`, `batch` (`volume`, `entries`: `path`, `kind`), `driveFailed` (`volume`, `message`), `error` (`message`, a rejected request; the helper keeps serving) and the terminal `died` (`reason`). The helper forwards only entries at, under or directly beside an armed root, because a filesystem mark reports the whole filesystem. It writes stdout through the raw descriptor, so a write to a closed pipe fails, and it exits on stdin end-of-input (0), a failed stdout write (2) or after `died` (3); a non-root start exits 1. The first stop reason selects the exit code, including when the terminal `died` frame cannot be delivered (source death selected 3, the `died` write then fails, and the helper still exits 3). Whenever the helper decides to stop (stdin EOF or a read failure, a failed stdout write, or source death after `died`) it starts one shutdown deadline of one second, even while stdin is still open. Pending terminal frames drain in order while the client can read them. If cancellation, native work, source disposal or terminal delivery is still pending at the deadline, the helper exits 4 and the kernel releases its descriptors. The helper writes no GitWizard state; the published apphost extracts its native libraries before managed startup (see [Linux Live elevation](manual-test-plan.md#linux-desktop-live-elevation-pkexec)). The test assembly calls `LinuxWatchHelperLaunch.ForbidPkexec()`, which refuses any start info whose file name is `pkexec`, bare or as a path. Until the helper's `hello` arrives, the launched process is pkexec still running as the caller and showing its dialog, and nothing is written to its stdin (pkexec reads none before it authenticates, so a large arm line could fill the pipe); cancelling the arm or disposing then terminates pkexec through `LinuxWatchHelperProcess.Terminate` (SIGTERM), which closes the dialog, and that self-caused end is neither an authentication failure nor a death. After `hello` the helper is root and is never signalled: cancelling the arm only abandons the caller's wait for the answer, while the arm request's pipe write is cancelled only by disposal, which also abandons a pending write, waits a bounded time for the input gate, closes stdin and waits a bounded time for the helper to exit. While arming, the helper does not forward the source's per-root readiness changes; it sends exactly one `readiness` frame carrying the settled full status list after the arm finishes and before `armResult`, so the arm costs one list however many roots the desktop lists, and later readiness changes (watch faults, exclusions) each send their own frame. Every multi-root transition is one snapshot and one event at its source, never a loop of per-root publishes: `FanotifyVolumeChangeSource` publishes its arm marks, an `fanotify_init` failure and a terminal pump failure each once (so source death sends exactly one `readiness` frame carrying every root excluded with the original reason, then `died`), and `ElevatedHelperVolumeChangeSource` publishes its local exclusions, a launch failure and a helper death once each. The client merges each `readiness` frame over the roots it excluded locally in one pass keyed by the watch key and sorts once, so those stay visible. A `dotnet` host executable path (`dotnet GitWizardUI.dll`) is refused before any launch with a fixed sentence that Live elevation needs the GitWizardUI executable itself. Before the helper's `hello`, the exit code is pkexec's: 126 reports that authentication was cancelled. Exit 127 can mean the dialog was dismissed, authorization failed, or no polkit authentication agent is available. A pkexec start that fails with file-not-found reports that polkit's pkexec is not installed and that starting GitWizardUI as root needs no prompt; any other start error (permissions, for example) reports the generic helper-start failure. Those words become the arm error for every root, so the coordinator returns an unusable startup and the UI shows `Live watch could not start: <message>` with Live off. Any helper end the client did not request excludes the roots (only those not already excluded, so a root excluded at arming or by the helper's terminal `readiness` frame keeps its own reason, and nothing is published when none remain) and raises `SourceDied` once, replayed to a subscriber that attaches later; the UI stops Live and reports it. The client implements `IVolumeReadiness` (`FilesystemMarks`), `IPumpLifecycle` and `IVolumeChangeDiagnostics` (drive failures only), so readiness and errors read as they do in process.

## Membership and batching

`RepositoryWatchService` is the platform-agnostic layer on top: it groups tracked roots by volume, maps change batches through `GitWizard.RepositoryChangeFilter.ClassifyEntry`/`TryClassifyMovedInCandidate`, and dedupes/debounces per window. The filter set is live: a repository whose `.git` creation classifies under a search root (or is probed from a moved-in candidate) is adopted into that volume's running filter, and a deleted repository's root is dropped, so repositories created while Live runs are tracked for changes without restarting Live. Directory renames arrive as `Deleted` + `MovedIn` (see `IndexChangeMapping`): a `MovedIn` path under a tracked root classifies as `Changed`, while an untracked one under a search root is probed once at flush time for `<path>\.git` (a directory, or a file for a gitfile worktree) and surfaces as `Created` on a hit, skipping ignored and temp-excluded paths. Probe-emitted `Created` events flush after the window's `Deleted` events so the UI's pending-delete rename correlation sees the old root first. It subscribes to optional drive diagnostics and optional `IVolumeScanProgress` before arming and detaches on shutdown, publishing immutable `ScanErrors` snapshots for initial scan errors and later watch failures plus immutable `ScanWarnings` journal-hint snapshots, where a mid-run `JournalWarningDetected` replaces the same drive's earlier hint, and immutable `CapacityWarnings` snapshots copied from the source's `CurrentCapacityWarnings` at arm and on every `CapacityWarningsChanged`; both warning kinds raise `ScanWarningsChanged`. It re-raises `ScanProgress`. `ScanErrorsChanged` fires outside the error lock, so a warning does not depend on a repository event. Sources without diagnostics retain their existing watch behavior.

`RepositoryChangeFilter` is I/O-free and cross-platform-testable. It finds the longest tracked root containing a path by looking up the path's ancestors in per-syntax root tables (Windows folds case, POSIX does not), so classification costs the path's depth, not the number of tracked repositories. `AddRepositoryRoot` and `RemoveRepositoryRoot` mutate the tracked root set mid-run, single-threaded on the watch pump. `ClassifyEntry` is path-based and emits Changed/Created/Deleted for one entry; `TryClassifyMovedInCandidate` separately reports `MovedInCandidates` (untracked directories renamed into a search root, or a case-only rename of a tracked root, left for the service layer to probe - the filter itself never touches the filesystem). Both respect configured ignored paths and the temp-directory exclusion (`includeTempDirectories`). `ClassifyEntry` also drops lock-only noise: an entry inside a tracked repository's `.git` directory, at any depth, whose final component ends with `.lock` (`index.lock`, `HEAD.lock`, `refs/heads/x.lock`, `worktrees/<name>/index.lock`) is not a change, because git takes and releases those files for read-only commands such as `git status` and the journal records each one. The rule is a fixed suffix on a fixed directory, always on, with no setting. A batch is reported as changed when it holds any other entry for the repository: a real index rewrite renames `index.lock` onto `index`, which the journal mapping delivers as `Deleted` for `.git\index.lock` plus `Created` for `.git\index`, and `.git\index` is not a lock file. A `.lock` file in the working tree (`Cargo.lock`) is an ordinary change. Under `-v`, the pump logs `Live watch: <root> changed; first triggering path <path>` each time a `changed:` event is queued. Paths compare through `GitWizard.Watch.WatchPath`, which retains a path's syntax (Windows-rooted vs POSIX) instead of rewriting separators, so a POSIX root is reported back as `/repos/repo-a` rather than `\repos\repo-a`.

## Consumers

`Program.cs` dispatches the elevated `--broker` child through `ElevatedEntryPoint.RunBrokerIfRequested` before normal startup. `--watch` uses the platform source factory (`IndexVolumeChangeSource` on Windows), prints `changed:` / `created:` / `deleted: <root>` (`changed:` means a tracked repository saw activity other than transient git lock files), prints each new or changed `scan error on <drive>: <message>` once while the stream is live, prints each journal hint line when it first appears and again when its wording changes (a live-watch loss rephrases the drive's arm-time hint), and prints each drive's capacity warning once as `Index on <drive>: could not store a journal change (<detail>). ... Restart git-wizard --watch to rescan <drive>:.` without prompting. CLI `--watch` runs `RepositoryDiscoveryCoordinator.PrepareWatchAsync` with the readable cached list as retained exact roots, so cached repositories on drives outside the configured search roots stay in discovery and in the journal watch's selected drive set; it replaces `repositories.txt` only with a publishable outcome. Repositories created since the previous cache write are therefore tracked without a rename. Discovery respects the configured ignore, hidden-directory and temp-directory policies. This adds startup latency at each CLI watch start; it does not launch an additional MFT broker or elevation prompt. An empty discovery clears the repository-list cache and the CLI reports that there is nothing to watch; an unusable discovery preserves the previous list and exits 1.

`LiveWatchController` forwards `ScanErrorsChanged` and `ScanProgress`; the UI shows "Scanning D: (n of N), x of y records" with a progress bar next to the amber Live button until the watch reports started (green), the start fails, or Live stops. The UI posts warning changes through its dispatcher even without repository events. A drive-specific failure keeps Live active on healthy drives. A Live run that ends in source death keeps the drives' journal hints and capacity warnings on screen; a user-initiated stop, a failed start and an unusable startup clear them. Capacity warnings show as orange lines under the journal hints and as cards in Settings' Journal Warnings section; a card's **Rescan** button stops and restarts Live (`LiveWatchViewModel.RestartLiveToRescanAsync`), whose watch preparation rescans the flagged drive, and is refused with a reason on the card while a refresh runs or Live is unavailable. Terminal loss retains the existing stop policy and at most three elevated respawns. An unelevated Linux desktop is not elevated, so a declined prompt, failed authorization or helper death never respawns or prompts again.

## Readiness

`Started` and green Live describe pump startup, not catch-up completion. `IVolumeReadiness` exposes immutable per-volume `CatchingUp`/`CaughtUp`/`Excluded` state and backing origin. Windows readiness follows version-checked library watch observations and catch-up waits; all views on a volume must catch up before that volume is ready. Linux marks report `CaughtUp` when installed, with no historical backlog. `RepositoryWatchService.Ready` fires once after startup batches are delivered and readiness settles with a caught-up volume; terminal/cancellation state wins publication races.

`LiveWatchController` forwards `Ready`, `VolumeReadinessChanged` and `StartupProgress`; the CLI prints `ready:` (grammar in README) and, under `-v`, timestamped `drive:`/`startup:` lines. `RepositoryDiscoveryCoordinator.PrepareWatchAsync` takes an `IProgress<WatchStartupProgress>` because the arm and catch-up complete before any consumer holds the source; `RequestingElevation`/`BrokerConnected` come from `BrokerSession.Connecting`/`Connected`, or on Linux from the pkexec helper source's `IElevationConnection.Connecting` (the launch) and `Connected` (the helper's `hello`). Broker process existence is never readiness evidence. Reconciling the startup buffer collects every buffered entry's reconciliation targets first and probes each distinct target once, in first-seen order. Only a path that can be a repository root is a target: the parent of a `.git` entry; the entry's directory when the entry's leaf is `HEAD`, `objects` or `refs` or its directory's name ends in `.git` (a bare repository created in the window journals no `.git` leaf; a directory named exactly `.git` and anything inside a `.git` directory never qualifies); and the nearest repository root already in the inventory at or above the entry, so a known repository deleted with only a deep child entry buffered is removed. An ordinary file costs no probe, so the probe count is bounded by the repository-relevant paths, never by the number of buffered files. Reconcile needs no probe of an unknown directory holding only working-tree entries: the discovery read that precedes it is taken after catch-up, so the index inventory already carries every repository whose `.git` predates the catch-up tip and the buffer carries every `.git` created after the cursor; `WatchStartupProgress.Completed` and `Total` count probed targets against the distinct total and the CLI prints `startup: reconciling <probed>/<total>` every 50,000 targets. Cancellation is observed per buffered batch, per probed target, and per batch of the startup replay in `RepositoryWatchService.PumpAsync`; that replay reports no progress of its own. The UI still correlates delete/create pairs by remote URL.

Desktop readiness uses one reserved, nonwrapping toolbar line; per-drive state, origin, and failure reasons are shown only in its tooltip and the Index Cache Status window, sharing LiveWatchViewModel.LiveVolumes. The readiness tooltip and Index Cache Status window list recent watch transitions separately from current volume readiness. Faulted and Recovering are retained as separate observations even when recovery is immediate. The list retains up to 64 observations for 30 seconds and clears on an explicit Live stop or a new run. It is in-memory only and is not part of report.json. UI summary updates on later snapshots do not re-emit RepositoryWatchService.Ready. Cache-status refresh remains independent of live readiness updates.
